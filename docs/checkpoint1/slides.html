Topic and objectives

Topic 3: an online auction application

Users open auction rooms and queue items for sale. Others join a room and bid on the item on the floor, one item at a time, until the queue is empty.

Real-time bidding

Every accepted bid is pushed to everyone in the room at once.

English auction

A bid must beat the current price by at least 10,000 VND. Buy-now ends the item at once.

Anti-sniping timer

Everyone is warned at 30 seconds left. A late bid resets the clock to 30 seconds.

Own protocol

C server on Linux, raw TCP sockets, no socket libraries and no proxy server.

Hòa: This is our system architecture. On the left is the client, which is my part. Each client keeps one TCP connection open for the whole session. Inside the client there are two threads: the GUI thread, and a network thread that waits in recv(). The network thread is needed because the server can push events at any time. It passes each message to the GUI with a Qt signal. In the middle are the three kinds of message: requests, responses, and events pushed by the server. On the right is the server, which Huy builds. It runs in one process and one thread. The select() loop wakes up when a socket is ready, or when the nearest auction deadline arrives, so we do not need a separate timer thread. Every client has its own receive and send buffer, because TCP is a byte stream. The parser splits each line and the dispatcher calls the right module. Now Minh will explain our protocol.

Application protocol

Framing

  • UTF-8 text, one message per line
  • Fields split by |, line ends with \n
  • At most 4096 bytes per message
  • Escapes in a field: \\ for a backslash, \p for |, \n for a newline
  • One recv() may hold part of a message, one message or many, so each side keeps a buffer

Three kinds of message

Request, client to server: always gets exactly one response

Response: OK_… on success, ERR|code|message on failure

Event, server to client: pushed at any time, even while the client waits

LOGIN|binh|1234
OK_LOGIN|binh
BID|1|505000
ERR|E_BID_TOO_LOW|Minimum bid is 510000

Minh: Thank you, Hòa. We call our protocol OAP. Every message is one line of UTF-8 text, with fields separated by a pipe. Because TCP has no message boundaries, each side keeps a receive buffer and cuts messages at the newline. On the server Huy’s code does this, and on the client Hòa’s network thread does it. There are three kinds of message. A request always gets one response. Events are pushed by the server at any time, which is why the client needs its own network thread.

Minh: Now that we know the messages, here is one bid going through the whole system. One: the user clicks Bid and the GUI sends the BID line. Two: select() sees data, the server reads it and cuts out one full line. Three: the auction module, my part, checks the rules. Four: the server queues OK_BID for the bidder and EVT_NEW_BID for every member of the room. Five: on each client the network thread receives the event and tells the GUI through a Qt signal. Because the server has one thread, two bids that arrive together are handled one after the other, so no locks are needed.

Rules the server enforces

+10,000

VND, the minimum raise over the current price. The first bid must beat the start price by the same amount.

30 s

left: everyone in the room gets a warning. A bid inside this window resets the clock to 30 seconds.

1 room

per user at a time. Only the room owner adds items and starts the auction, and the owner cannot bid.

Minh: These are the rules the server checks, not the client. A bid must be at least 10,000 VND above the current price. When 30 seconds are left, the server warns everyone, and any bid in that window resets the clock to 30 seconds, so nobody can win by bidding in the last second. The server sends the number of seconds left, and each client counts down by itself, so the server does not send a message every second and a wrong clock on a client does not matter. Now back to Huy.
